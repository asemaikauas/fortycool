# FortyCool agent service

FortyCool is an evidence-first thermal decision service for a data-center digital twin. This
milestone provides the deterministic tools and typed contracts that an LLM planner can call.

The default provider is a reproducible fixture. Set `FORTYCOOL_THERMAL_PROVIDER=live` to use the
validated FortyGuard adapter. Live mode is deliberately hybrid: spatial temperature heatmaps and
forecast temperatures come from FortyGuard, while BMS telemetry and environmental fields remain
simulated unless the operator uploads facility telemetry.

## What is implemented

- Typed analysis requests and responses
- Logical planning, temperature, asset-modeling, decision, investment, and audit agents
- Reproducible data-center BMS simulation driven by thermal conditions
- Site-versus-control difference-in-differences and eligibility-hour analysis
- Satellite land-cover context and regional-control matching
- Google Dynamic World annual 10 m land-cover history with complete-coverage gates
- Two-stage public data-center discovery with an explicit no-winner outcome
- Cooling-demand and inlet-temperature models with a held-out-day backtest
- Constrained enumeration of 12-hour operating scenarios
- Safety vetoes and an explicit `hold_current_settings` path
- Indicative energy and NPV translation
- Evidence lineage and inspectable agent trace
- FastAPI endpoints and a JSON CLI
- Validated CSV telemetry uploads with an evidence-based optimization hold
- Agent-callable workflow endpoints and machine-readable JSON schemas
- SQLite-backed completed runs and live server-sent agent events
- Low-level asynchronous FortyGuard submission, polling, and cache client
- Live FortyGuard GeoJSON heatmap normalization with a facility core and local control ring
- Premium Satellite Segmentation normalization without retaining Base64 imagery in evidence
- Four-candidate regional-control selection by current land-cover similarity
- Equal-weight regional control zones inside a single expanded historical heatmap AOI
- Twelve hourly FortyGuard forecast calls with bounded concurrency and per-activity evidence
- Historical `tcm` and below-threshold `exceedance` screening with explicit coverage fallbacks
- GPT-4o copilot answers grounded in completed-run metrics, warnings, and evidence IDs
- A downloadable, evidence-linked ThermalDrift investment memorandum in PDF format
- A verified saved-demo selector with strict FortyGuard, Dynamic World, and no-backcast gates

## Data integrity

The service uses four important labels:

- `observed`: returned by a real source such as FortyGuard
- `uploaded`: supplied by the user and accepted by the telemetry validator
- `simulated`: generated by the digital twin or fixture provider
- `inferred`: calculated from other records
- `assumed`: a demo value that has not been confirmed by an operator

Fixture results must never be presented as live FortyGuard observations. The operating recommendation
is advisory only and cannot control real equipment.

## Run locally

The machine's existing Python environment already contains the runtime dependencies. From this
directory:

```bash
PYTHONPATH=src python3 -m fortycool_agents.cli --request examples/demo_request.json
```

Run the API:

```bash
PYTHONPATH=src uvicorn fortycool_agents.api:app --reload --port 8000
```

The integrated dashboard is served by the same process, so no separate frontend server or browser
API key is required:

```text
http://127.0.0.1:8000/dashboard/pages/site_setup.html
```

The dashboard starts the complete ThermalDrift, 12-hour operations, and investment workflow through
`POST /run-jobs`, renders the named SSE `trace` events while agents work, and then resolves metrics,
charts, recommendations, assumptions, and evidence by their stable response IDs. BMS telemetry is
simulated by default and visibly labelled; operators can instead upload a validated CSV from Site
Setup. All actions remain advisory-only.

## Agent boundary

The application currently uses a deterministic planning agent so the complete workflow is testable.
The team's LLM layer can replace that planner while keeping the tool behavior and response contract
unchanged. Important calculations must remain in deterministic tools; the LLM should plan, select
tools, and explain tool results.

The tool catalog is available at `GET /tools`. The stable output fields intended for the dashboard are:

```text
run_id
status
confidence_tier
metrics
recommendations
charts
evidence
trace
assumptions
warnings
```

The three `/agent-tools/*` routes are the direct integration boundary for an LLM planner. They accept
the same typed analysis request as `/runs`, but force the appropriate workflow so a model cannot
silently skip required specialist and safety stages.

For the interactive dashboard, submit the same request to `POST /run-jobs`. The endpoint returns
`202 Accepted` with a run ID, executes the workflow in the background, and publishes trace events at:

```text
GET /run-jobs/{run_id}/stream
```

The stream uses standard `text/event-stream` messages named `trace` and `terminal`. Completed analysis
responses are saved to SQLite and remain available through `GET /runs/{run_id}` after a service
restart. Set `FORTYCOOL_DB_PATH` to choose the database location; the default is
`.fortycool-data/runs.sqlite3`.

### Verified demo and investment memorandum

Site Setup includes **Load Verified ThermalDrift Demo**. The action does not fabricate a result or
silently make a new provider request. It selects a persisted completed run only when all of these
backend gates pass:

- annual FortyGuard heatmap evidence contains at least three consecutive observed years;
- the FortyGuard evidence contains no calibrated backcast years;
- observed Google Dynamic World history is present; and
- the Dynamic World record confirms historical coverage for the selected controls;
- the regional-control similarity gate is accepted and those controls are used in the FortyGuard
  history; and
- the drift and local-buildout metrics link directly to the qualifying provider evidence.

The returned manifest discloses whether the saved run contains an observed forecast heatmap and the
data class of its 12-hour operational series. A saved demo may therefore have verified real
ThermalDrift inputs while its BMS, forecast, and optimization panels remain visibly simulated or
inferred.

Every persisted run can be exported at `GET /runs/{run_id}/memo.pdf`. The deterministic memo includes
the difference-in-differences conclusion, investment metrics, annual thermal and land-cover tables,
assumptions, warnings, operational data classes, and an evidence appendix. Metric evidence IDs link
back to the run's immutable evidence endpoints. The report is an advisory screening deliverable, not
an engineering design or valuation opinion.

## Uploaded telemetry

Send CSV as a raw request body rather than multipart form data:

```bash
curl -X POST http://localhost:8000/telemetry/uploads \
  -H 'Content-Type: text/csv' \
  --data-binary @facility.csv
```

Required columns:

```text
timestamp
it_load_kw
cooling_power_kw
server_inlet_temperature_c
```

Recommended control columns:

```text
supply_air_setpoint_c
chilled_water_supply_c
fan_speed_percent
economizer_state
```

The validator requires at least 14 days of approximately 15- to 60-minute data, normalizes it to
hourly cadence, rejects invalid power/temperature values, removes unknown columns, and attaches a
new upload ID. Uploads are currently stored in memory and expire when the service restarts.

If the history does not contain enough variation in setpoints or fan speed, the safety agent returns
`hold_current_settings`. A forecast model may fit historical demand well without having evidence for
how a control change would affect the facility; FortyCool treats those as separate questions.

## Live FortyGuard integration

`FortyGuardClient` reads `FORTYGUARD_API_KEY` from the environment and never from a request body.
It supports asynchronous submission, bounded status polling, terminal failure handling, and cached
responses. Copy `.env.example` to `.env`, insert the key, and launch live mode with:

```bash
set -a
source .env
set +a
export FORTYCOOL_THERMAL_PROVIDER=live
PYTHONPATH=src uvicorn fortycool_agents.api:app --reload --port 8000
```

Live mode uses one 60 m heatmap per forecast hour so the dashboard receives a genuine 12-hour
temperature timeline rather than a range average. It returns the first forecast map as a GeoJSON
chart named `fortyguard_heatmap` and records every FortyGuard activity ID in evidence metadata.

Historical drift uses a matched seasonal month for each year: `tcm` supplies site/control
temperatures and `exceedance` supplies hours below the configured threshold. Eligibility is
annualized for screening and is not utility-grade full-year accounting. If FortyGuard returns no
tiles for an older year, the provider creates a fixture backcast calibrated to the earliest observed
year, labels the combined dataset `inferred`, and adds the affected years to both warnings and
evidence. It never labels these backcasts as observed.

The demo baseline is 2022, the earliest year verified for both July and August `tcm` and
`exceedance` tiles at the Northern Virginia demo AOI. The primary 2022–2026 workflow therefore does
not depend on a 2021 backcast. Earlier baselines remain available for other sites, but any coverage
gap is disclosed through the fallback behavior above.

The live provider does not pretend that the public weather API is a BMS. Dense training telemetry is
still generated by the data-center digital twin or supplied through `POST /telemetry/uploads`.

### Satellite context and regional controls

Set `FORTYCOOL_URBAN_PROVIDER=dynamic_world` to use Google Dynamic World as the historical
land-cover provider while keeping `FORTYCOOL_THERMAL_PROVIDER=live` for FortyGuard air
temperature. Dynamic World is queried through Earth Engine as one batched `computeFeatures`
calculation covering the site, four control candidates, and every requested year. The provider uses
June-August mean class probabilities at 10 m resolution inside 500 m AOIs. Each AOI/year must pass
minimum scene-count and valid-pixel gates, and all selected controls must have complete history.

The returned evidence includes the `GOOGLE/DYNAMICWORLD/V1` dataset ID, Earth Engine project
endpoint, workload tag, seasonal window, acquisition bounds, scene counts, valid-pixel counts,
control coordinates, and annual site-versus-control `built`, vegetation, and bare-ground shares.
FortyCool calculates local excess built-surface change and, where at least three matched years exist,
reports the temporal correlation with the site-control thermal gap. The correlation is explicitly an
attribution hypothesis and never a causal claim.

Earth Engine requires an enabled and registered Google Cloud project plus user or service-account
credentials. After installing the project dependencies, authenticate and configure the providers:

```bash
earthengine authenticate
export EARTH_ENGINE_PROJECT=your-google-cloud-project
export FORTYCOOL_THERMAL_PROVIDER=live
export FORTYCOOL_URBAN_PROVIDER=dynamic_world
```

Application Default Credentials and `GOOGLE_APPLICATION_CREDENTIALS` are also supported by the
Earth Engine client. Never commit a service-account JSON key. If Dynamic World is not configured,
`FORTYCOOL_URBAN_PROVIDER=live` keeps the existing FortyGuard Satellite Segmentation integration.

In live mode the `UrbanChangeAgent` uses FortyGuard Premium Satellite Segmentation for the site and
four candidate points 3 km north, east, south, and west. Model-specific segment labels are mapped to
stable land-cover groups. The three candidates with the highest current land-cover similarity must
all pass a configured quality threshold before they are passed to the historical thermal provider.
If they fail, FortyCool records the rejected candidates and uses the disclosed local outer ring; it
does not call weak comparisons "matched controls."

The historical provider requests one expanded AOI per year and analytic type. It calculates the site
core and each selected control core independently, then gives the three control-zone means equal
weight. This keeps the historical request count bounded while preventing a dense control zone from
dominating the comparison. Evidence records the coordinates, match scores, tile counts, activity IDs,
and control method.

Satellite Segmentation is a Premium endpoint. The completed response contains an `image_year`, but a
historical `date_time` request does not necessarily select historical imagery. At the demo site both
the 2022 and 2026 requests currently resolve to a 2026 image. FortyCool therefore reports current
built-surface and tree-canopy shares, but emits `satellite_change_status=not_available` and does not
calculate a historical land-cover delta when the two image years are the same. Fixture mode contains
a clearly labelled simulated change series so the complete UI flow can still be demonstrated.

Current imagery can support control matching, but it cannot prove that a control did not develop over
the historical window. The run includes this as a warning. Historical causal attribution remains a
screening result until distinct dated imagery or another auditable historical land-cover source is
available.

### Public-site discovery

`POST /agent-tools/site-discovery` is a two-stage discovery agent. With an empty JSON request it uses
four publicly listed Northern Virginia facilities: Digital Realty ACC5, Digital Realty IAD24,
Equinix DC14, and Digital Realty VA3. Operator names and addresses are linked to the operators'
official facility pages; coordinates are geocodes of those reported addresses. Custom requests can
supply one to twelve alternative candidates.

The first stage makes only baseline and latest July `tcm` requests and calculates local
difference-in-differences against a disclosed outer ring. By default, only sites at or above `0.10°C`
are shortlisted. The second stage runs the configured satellite provider, requires all three selected
controls to clear the land-cover match threshold, requires distinct historical land-cover coverage,
and then runs the complete annual
sequence against those controls using the existing July screening methodology. A site is a winner
only if it clears every gate without a historical coverage backcast; this is multi-year screening,
not a full-year utility-grade reconstruction.

```bash
curl -s -X POST http://127.0.0.1:8000/agent-tools/site-discovery \
  -H 'Content-Type: application/json' \
  -d '{}' | jq
```

Fixture mode demonstrates the complete positive path and clearly labels all thermal outputs as
simulated. It currently selects ACC5 with a simulated `0.486°C` validated drift and `0.950` control
match; these are not claims about Digital Realty. In the verified live screen, ACC5 measured
`0.0069°C` and the other three candidates were effectively flat, so the correct live result is
`no_qualified_candidate` and Satellite deep validation is not invoked. This negative result is an
important integrity feature, not a hidden fallback.

## GPT-4o copilot

Set `OPENAI_API_KEY` and optionally `FORTYCOOL_COPILOT_MODEL` (the default is `gpt-4o`). The key is
read only from the server environment. The copilot uses OpenAI's Responses API with strict
Structured Outputs and `store: false`.

The copilot operates only on a completed analysis. It receives a compact context containing metrics,
recommendations, warnings, assumptions, chart summaries, the agent trace, and the evidence index.
Raw GeoJSON polygons are replaced with a feature count before model submission. Deterministic
calculations and safety verdicts remain authoritative; the model cannot change them or control
equipment.

```bash
curl -s -X POST "http://127.0.0.1:8000/runs/$RUN_ID/copilot" \
  -H 'Content-Type: application/json' \
  -d '{
    "question": "Explain the recommendation and its main risks.",
    "audience": "operator"
  }' | jq
```

Supported audiences are `operator`, `investment_committee`, and `technical_reviewer`. The response
includes the GPT-4o response ID, model name, concise answer, findings, cautions, suggested follow-up
questions, and validated evidence IDs that can be resolved through the existing evidence endpoint.
